# samples 示例文档

三份**虚构**文档，用于开箱验证上传、混合检索与引用回链。公司、产品、条款、联系方式均为虚构，与任何真实企业或个人无关；请勿把这里的内容当作真实资料。

| 文档 | 一句话说明 | 适合演示 |
|---|---|---|
| [`service-manual.md`](service-manual.md) | 虚构的「星澜云」知识库产品与服务手册：服务版本、部署方式、SLA、试用与计费 | 版本对比、列举型问题 |
| [`attendance-policy.md`](attendance-policy.md) | 虚构的考勤与休假制度：打卡、假期天数、请假审批、加班调休、出差 | 多条目列举、流程型问题 |
| [`support-faq.md`](support-faq.md) | 虚构的客户服务 FAQ：支持渠道、工单优先级与响应时效、升级与维护 | 表格型时效、跨文档问题 |

## 上传

服务启动后（见根目录 README「快速开始」），一次上传三份文档：

```bash
for f in samples/service-manual.md samples/attendance-policy.md samples/support-faq.md; do
  curl -s -X POST http://127.0.0.1:8000/upload-doc -F "file=@$f"
  echo
done
```

预期每份返回 `{"msg":"文件入库成功","chunk_count":3}`（共 9 个文本块；改动文档内容后块数会变）。

## 示例问题

三个问题按「单文档列举 → 易混淆并列项 → 跨文档」排列，覆盖稠密与关键词两条召回通道。

### 1. 列举型：假期有哪几类、各几天

> 员工可以享受哪些假期？分别有多少天？

- 为什么体现混合检索：提问没有出现文档里的专有名词，靠稠密召回找到「假期种类与天数」段；「哪些」触发列举型加深候选，BM25 再用「假期」「天数」等 token 补精确匹配。
- 预期答案：年假 5/7/10/15 天（对应满 1/3/5/10 年）、病假 15 天（带薪上限）、事假 10 天、婚假 10 天、产假 98 天（叠加地方奖励假）、陪产假 15 天、丧假直系 3 天 / 旁系 1 天。
- 预期来源：`attendance-policy.md`「二、假期种类与天数」。

### 2. 列举型 + 并列项：服务版本及各版本支持

> 星澜云有哪些服务版本？每个版本分别提供哪些支持服务？

- 为什么体现混合检索：三个版本在原文里是并列短句，稠密召回容易只命中其中一个；关键词通道对「基础版 / 专业版 / 旗舰版」精确命中，加权 RRF 融合后保住整段对比。
- 预期答案：基础版（社区支持，不含工单）、专业版（工单支持 + SSO 单点登录）、旗舰版（专属客户成功经理 + 7×24 小时工单支持 + 可选私有化部署）。
- 预期来源：`service-manual.md`「二、服务版本」。

### 3. 跨文档：旗舰版遇 P1 故障的渠道与时效

> 旗舰版客户遇到 P1 严重故障时，应该通过哪些渠道提交工单？首次响应时限是多久？

- 为什么体现混合检索：答案分在两份文档——「旗舰版、7×24」在 `service-manual.md`，「P1、15 分钟、支持渠道」在 `support-faq.md`。只有检索层保留多文档候选并做文档级聚合，才可能把两边的块一起送进上下文。
- 预期答案：渠道为在线工单、企业微信服务群、服务邮箱；P1 首次响应 15 分钟内，旗舰版 7×24 小时全天候处理。
- 预期来源：`support-faq.md`「支持渠道」「工单优先级」+ `service-manual.md`「服务版本」。

## 自检

以上每个预期答案都能在三份文档原文中逐条找到（可直接 `grep` 核对）；问题措辞没有照抄文档标题，用于验证检索而不是记忆。若答案中出现文档里没有的数字或条款，说明模型没有严格基于资料，请检查 `prompts/system.md` 是否被改动。
